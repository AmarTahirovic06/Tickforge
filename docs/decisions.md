Aug. 30th: Countdown direction. You count down rather than up. Why: comparing against zero is a fixed, cheap check regardless of message length. Counting up would mean storing the target separately and doing a full 16-bit comparison every cycle.
Transition threshold. The return to S_LEN fires when byte_count == 1, not == 0. Why: at that point the byte arriving is the last body byte, and the state assigned at that edge is what the FSM uses for the next byte — which is the next message's first prefix byte. Checking zero would leave you in S_BODY one cycle too long and consume that prefix byte as content. 

Sep. 9th: Decided to use byte_pos to count up rather than derive from byte_count. I went with a separate counter. The window conditions would read byte_pos >= 24 && byte_pos <= 31 which verifies line by line the ITCH file's own spec offset table. Deriving it would need the message length stored in the register anyways, I'm not doing that theres no point. Same hardware cost regardless, and would put a subtract in the path every cycle instead of a magnitude compare. Offset bugs are silent and expensive, readability against the source spec wins any day.
Byte_pos & is_trade both carry stale values between messages, during a run I discovered pos=44 trade=1 at i=0 in the log, in addition to the test failing. After adding a probe in test_framer to figure out the byte sequence between where it was breaking, I discovered the stale values. Both are only read during S_BODY, and by the time a body starts, the length branch has reset byte_pos and the type byte has updated is_trade. Clearing them at message end would cost register with no benefit, so I'm writing it down for the record stating it is not a bug, I'm simply documenting it. 
byte_pos <= byte_pos + 1 was originally nested inside the byte_count == 1 branch. It would advance one message instead of one byte, so the window never reached 24, extraction would return 0x0, with no other visible issues. Verilator also did not find a complaint. Found it by logging byte_pos, is_trade, & ticker_window per byte. 

Sep. 14th: Figuring out which symbols fired most led me to creating the collision test, found the 1000 highest firing symbols out of 3445, useful in determining the BRAM budget I have to work with. Next I took those 1000 symbols, made them as a fixed input set, and pointed each symbol to a specific BRAM index. During initial testing, 3445 fired at least once, needing roughly 3445 Kbits of BRAM. Wouldn't fit. The coverage curve showed marginal fires per symbol after 1000, so I made that the baseline. I took 87.9% coverage, for 2200 Kbits of BRAM. 
Spent the 2nd day mapping tickers to indices, the actual collision work itself. At first I tested three XOR-fold functions in collisiontest.py, all failed badly. the raw low bits put all 1000 symbols on a single index because space padding makes the low bytes identical. So I widened to 12, 14, 16 bits, it helped but plateaued. Even at 16 bits I had 65536 slots for 1000 keys, 356 symbols were still colliding, I knew that was far worse than a good hash should do at 1.5% occupancy. Thats when I realized that the XOR folds weren't mixing with the ASCII properly, so I moved to zlib.crc32. Far better results, 202 collisions at 12 bits, 40 at 14, and 12 at 16. I tried different CRC-32 seeds to find one with zero collisions, but through 20 seeds I had identical results every time. 6 slots, 12 symbols. I thought the reason CRC-32 failed to give me zeros was a code bug, but after review I was incorrect. I realized that because all my inputs are exactly 8 bytes, mathematically, the seedless CRC combined with a fixed transformation determined by that seed. So if all inputs are the same, such as mine at 8 bytes, you get a bijection. one-to-one, onto, no two values merge into one. Eventually I settled with 17 bits, 2 collisions, 4 symbols, settling at around 1311 Kbits. 17 bits is our 'Goldilocks' zone, 16 being too low because I'm at 12 symbols for 655 Kbits, 18 being too high due to 2621 Kbits for 1 collision, also 2200 for the symbol state leaving nothing for the FIFO & histogram.
